# Mini URL Shortener（迷你短链服务）

一个用 **Java 17 / Spring Boot 3.2.1** 实现的短链服务：生成短码、把访问者重定向到原始链接，并提供按天的访问统计。

- 存储：内嵌 **H2 文件模式**（`./data/urlshortener`），无需安装任何数据库。
- 建表：启动时由 **Flyway** 自动完成。
- 启动：**一条命令**，默认端口 **8080**。

---

## 1. 构建与启动

前置条件：**JDK 17**（Maven Wrapper 会自行下载 Maven，不需要额外安装任何东西）。

```bash
./mvnw spring-boot:run          # Linux / macOS
mvnw.cmd spring-boot:run        # Windows
```

启动后服务地址为 <http://localhost:8080>，<http://localhost:8080/> 是一个最小可用的前端页面。

其他常用命令：

```bash
./mvnw clean verify             # 编译 + 运行全部测试
./mvnw -DskipTests package      # 打包为 target/url-shortener-1.0.0.jar
java -jar target/url-shortener-1.0.0.jar
```

可选配置：

| 配置项 | 默认值 | 如何覆盖 |
|---|---|---|
| 端口 | `8080` | `SERVER_PORT=9090 ./mvnw spring-boot:run` |
| `short_url` 使用的域名前缀 | `http://localhost:8080` | `APP_BASE_URL=https://s.example.com` |
| 数据库文件 | `./data/urlshortener` | 修改 `src/main/resources/application.yml` 里的 `spring.datasource.url` |

> Flyway 迁移脚本是按 H2 写的（用了 `GENERATED BY DEFAULT AS IDENTITY`、`TIMESTAMP(6)`）。
> 换成 MySQL/PostgreSQL 需要改写 `src/main/resources/db/migration/V1__create_schema.sql`
> 和数据源配置 —— 除这两处外，代码中没有其他 H2 相关的东西。

### Docker（另一种一键启动方式）

```bash
docker compose up --build       # 启动后访问 http://localhost:8080
```

H2 数据文件放在具名卷 `shortener-data` 中，因此 `docker compose down` 之后数据仍然保留。

## 2. API 使用

### 创建短链

```bash
curl -i -X POST http://localhost:8080/api/links \
     -H "Content-Type: application/json" \
     -d '{"url": "https://example.com/some/very/long/path?query=1"}'
```

```http
HTTP/1.1 201 Created
```

```json
{
  "code": "aB3xK9",
  "short_url": "http://localhost:8080/aB3xK9",
  "url": "https://example.com/some/very/long/path?query=1",
  "created_at": "2026-10-15T08:30:00.123456Z",
  "expires_at": null
}
```

校验规则（违反返回 `400 INVALID_URL`）：`url` 必填且非空；协议必须是 `http` 或 `https`；长度不超过 2048 个字符。

### 访问短链（重定向）

```bash
curl -i http://localhost:8080/aB3xK9
```

```http
HTTP/1.1 302 Found
Location: https://example.com/some/very/long/path?query=1
Cache-Control: no-store
```

### 查询短链详情

```bash
curl -i http://localhost:8080/api/links/aB3xK9
```

```json
{
  "code": "aB3xK9",
  "url": "https://example.com/some/very/long/path?query=1",
  "created_at": "2026-10-15T08:30:00.123456Z",
  "expires_at": null,
  "visit_count": 128,
  "last_visited_at": "2026-10-15T09:12:44.001Z"
}
```

### 按天统计（近 7 天）

```bash
curl -i http://localhost:8080/api/links/aB3xK9/stats
```

```json
{
  "code": "aB3xK9",
  "days": [
    {"date": "2026-10-09", "count": 0},
    {"date": "2026-10-10", "count": 3},
    {"date": "2026-10-11", "count": 0},
    {"date": "2026-10-12", "count": 17},
    {"date": "2026-10-13", "count": 42},
    {"date": "2026-10-14", "count": 51},
    {"date": "2026-10-15", "count": 15}
  ]
}
```

窗口为**含今天在内的最近 7 个自然日**，按**由旧到新**排序，无访问的日期**补 `count: 0`**。
"一天"按 **UTC** 划分。

### 错误响应

所有接口返回同一种错误结构：

```json
{
  "status": 404,
  "error": "NOT_FOUND",
  "message": "No short link with code 'zzzzzzz'",
  "timestamp": "2026-10-15T09:12:44.001Z",
  "path": "/zzzzzzz"
}
```

| 状态码 | `error` | 触发条件 |
|---|---|---|
| 400 | `INVALID_URL` | URL 缺失、非 http/https、长度超过 2048 |
| 400 | `INVALID_CODE` | 自定义短码不符合 `[A-Za-z0-9]{3,32}` 或命中保留字 |
| 400 | `INVALID_EXPIRY` | `expires_at` 不是未来时间 |
| 400 | `MALFORMED_JSON` | 请求体不是合法 JSON |
| 404 | `NOT_FOUND` | 短码不存在 |
| 409 | `CODE_ALREADY_EXISTS` | 自定义短码已被占用 |
| 410 | `LINK_EXPIRED` | 链接已过期 |
| 503 | `CODE_ALLOCATION_FAILED` | 未能分配到空闲短码（可重试） |

### 加分项接口与字段

| 功能 | 用法 |
|---|---|
| 自定义短码 | `{"url": "...", "code": "myalias"}`；已被占用返回 `409` |
| 链接过期 | `{"url": "...", "expires_at": "2026-12-31T00:00:00Z"}`；过期后 `GET /{code}` 返回 `410 Gone` |
| 分页列表 | `GET /api/links?page=0&size=20`（最新的在前），前端页面使用 |

## 3. 设计决策

### 3.1 短码生成 —— 随机 Base62，7 位，冲突重试

用 `SecureRandom` 从 `[0-9A-Za-z]` 中随机取 7 个字符（62⁷ ≈ 3.5 × 10¹² 种可能）。

- **为什么不用「自增 id 转 Base62」？** 连续短码会泄露链接总量，并且任何人都能把整个短码空间枚举一遍。
- **为什么不用「hash(url) 截断」？** 哈希是确定性的，与下面「重复 URL 给新码」的策略相矛盾（同一个 URL 需要能拿到多个短码），而且还得多加盐。
- **冲突处理：** 不预防，只**检测** —— `links.code` 的唯一约束会拒绝重复值，随后换一个新候选重试（最多 10 次，超出返回 `503`）。每次插入都在**独立事务**（`REQUIRES_NEW`）中执行；否则失败的 INSERT 会把外层事务标记为 rollback-only，导致后续每次重试都失败。

### 3.2 重定向状态码 —— 用 `302 Found`（不用 `301`）

`301 Moved Permanently` 会被浏览器无限期缓存，重复访问根本不会打到服务端，访问数就会静默少计 —— 对一个以计数为核心职责的服务来说这是致命的。
`302` 保证每次访问都回源，统计精确；代价是每次重定向多一个 RTT，另外加 `Cache-Control: no-store` 防止共享缓存重放响应。
如果不需要统计，`301` 反而是更好的选择（更快，且能把流量卸载到 CDN）。

### 3.3 重复 URL —— 始终生成**新**短码

同一个 URL 每次提交都得到不同的短码，这样不同活动/渠道可以各自独立计数与归因。
同时也让写入路径不存在「先查再插」的 upsert 竞态：创建就是一条 INSERT。
代价是相同 URL 会被存储多份，且没有跨短码的按 URL 汇总统计。
因此 `url` 列**不建索引** —— 它从不被查询。

### 3.4 按天统计的存储 —— 按天聚合表，而不是事件流水表

`link_daily_visit(link_id, visit_day, visit_count)` 每个链接每天一行。

- **聚合表的理由：** 存储量有上界（链接数 × 天数），读取 7 天窗口只是一次很小的范围扫描；对这种「重定向远多于创建」的读多写少服务，这才是能扩展下去的结构。
- **流水表的代价：** 会保留每一次访问，无界增长，今天的热路径会变成明天的全表扫描。它唯一的优点是提供了我们并不需要的信息（按小时下钻、独立访客数、换时区重算）。
- **原子性：** 自增语句是 `UPDATE ... SET visit_count = visit_count + 1 WHERE ...`，即运算在数据库里、在单行锁上完成，而不是在 Java 里读-改-写。两个计数器写在**同一个短事务**中，并且**先**执行总量对应的 `UPDATE links WHERE id = ?` —— 它持有的行锁会把同一链接的并发重定向串行化，于是后面「今日桶不存在则创建」这一步几乎不可能发生竞态。若 UPDATE 影响行数为 0，则以 `count = 1` 建桶；万一真的冲突（在不支持行级锁的数据库上），整个事务回滚后重放一次即可。已由 `RedirectConcurrencyTest` 验证（32 线程 × 20 请求，计数精确等于 640）。
- H2 2.2 既不支持 `INSERT ... ON CONFLICT DO UPDATE`，也不支持「先读后写」的原子 `MERGE`，因此「先更新，更新不到再插入，冲突则重放」是最可移植的做法。
- `links` 上的总访问数 `visit_count` 是刻意保留的冗余字段：一旦清理掉旧日期，聚合表就无法回答「总共多少次访问」。
- **日切分采用 UTC**，保证同一次访问无论服务部署在哪个时区都落进同一个桶。

### 3.5 数据库索引

| 索引 | 类型 | 理由 |
|---|---|---|
| `links.code` | UNIQUE | 既是短码唯一性的硬保证，也是重定向/详情/统计的查询路径 |
| `link_daily_visit(link_id, visit_day)` | UNIQUE | 让按天自增只命中一行锁、让 7 天范围扫描极小，并防止出现重复桶 |
| `links.created_at`（倒序） | INDEX | 前端使用的「最新链接」分页列表 |
| `links.url` | *（不建）* | 按上面的重复 URL 策略，它从不被查询 |

### 3.6 热链缓存（加分项）

Caffeine 缓存 `codeToTarget`（`maximumSize=10000`，`expireAfterWrite=10m`）缓存 `code -> (id, url, expiresAt)` 映射，而这正是重定向热路径唯一需要的数据。
只缓存**不可变**数据，**访问计数绝不进缓存**，因此缓存不会污染统计。
因为没有更新/删除接口，靠 TTL 过期就足以保证数据新鲜；唯一的显式 `@CacheEvict` 用于发现链接已过期时清除条目。如果以后加入编辑/删除接口，就必须在事务提交后再失效对应条目。

```
    ├── main/

    │   │   ├── config/          AppProperties（所有可调参数）
    │   │   ├── domain/          Link、LinkDailyVisit
    │   │   ├── repository/      Spring Data JPA（+ 原子自增查询）
    │   │   ├── service/         LinkService、RedirectService、VisitRecorder、
    │   │   │                    VisitCounter、LinkStore、CodeGenerator、UrlValidator、CodePolicy
    │   │   ├── error/           ApiException 体系（状态码 + 错误码）
    │   │   └── web/             LinkController、RedirectController、dto/、GlobalExceptionHandler

    │       └── static/index.html
    └── test/java/com/example/urlshortener/   27 个测试
```

分层严格为 controller → service → repository：controller 只负责绑定 HTTP，所有异常统一在
`@RestControllerAdvice` 中转换。

## 5. 测试

固化的验收用例清单见 **[`docs/TEST_CASES.md`](docs/TEST_CASES.md)** —— 37 条编号用例
（TC-001 … TC-037），每条都对应到场景、预期结果以及执行它的测试方法。

```bash
./mvnw verify
```

| 测试类 | 覆盖范围 |
|---|---|
| `LinkApiIntegrationTest` | 创建 → 重定向 → 详情 → 统计全链路，参数校验，404/409/410，非法 JSON，列表 |
| `RedirectConcurrencyTest` | 32 线程 × 20 次真实 HTTP 重定向 → 计数精确等于 640（无丢失更新） |
| `LinkStatsWindowTest` | 7 天窗口的边界、排序、补零 |
| `LinkTargetCacheTest` | 缓存写入与失效 |
| `Base62CodeGeneratorTest` | 短码长度、字母表、20 000 次生成无重复 |
| `UrlValidatorTest` | 每一条 URL 校验规则 |

每个集成用例都在 `@BeforeEach` 中重置数据库，结果不依赖执行顺序；所有时间计算都走注入的 UTC `Clock`。

### 手工冒烟测试

```bash
./mvnw spring-boot:run                                  # 终端 A
BASE_URL=http://localhost:8080 ./scripts/smoke-test.sh   # 终端 B
```

对运行中的实例执行 28 项检查（创建、重定向、统计、404/400/409/410、过期、50 次并发重定向）；
每项检查打印一行 PASS/FAIL，只要有一项失败就以非零码退出。

## 6. 关于水平扩展（超出本次范围）

之所以能接受 H2，前提就是单实例。要横向扩展的话：换成 PostgreSQL/MySQL，让多个无状态应用实例共享同一个库；短码分配仍用随机插入（唯一约束才是唯一事实来源，而不是某个计数器）；把每次请求的自增改成缓冲/队列化写入（例如 Redis `INCR` 定期落库，或批量 upsert），避免热门链接在同一个行锁上排队；并把 Caffeine 缓存放在共享的 read-through 层前面，在编辑/删除时显式失效。
