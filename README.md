# Mini URL Shortener

A small URL shortener service in **Java 17 / Spring Boot 3.2.1**: it issues short codes, redirects
visitors to the original URL, and reports per-link visit statistics.

- Storage: embedded **H2 in file mode** (`./data/urlshortener`) — no database to install.
- Schema: created automatically on startup by **Flyway**.
- Starts with **one command**, on port **8080** by default.

---

## 1. Build & run

Requirements: **JDK 17** (the Maven wrapper downloads Maven itself; nothing else is needed).

```bash
./mvnw spring-boot:run          # Linux / macOS
mvnw.cmd spring-boot:run        # Windows
```

The service is then available on <http://localhost:8080> and a minimal UI is served at
<http://localhost:8080/>.

Other useful commands:

```bash
./mvnw clean verify             # compile + run all tests
./mvnw -DskipTests package      # build target/url-shortener-1.0.0.jar
java -jar target/url-shortener-1.0.0.jar
```

Configuration (all optional):

| Setting | Default | How to override |
|---|---|---|
| Port | `8080` | `SERVER_PORT=9090 ./mvnw spring-boot:run` |
| Base URL used in `short_url` | `http://localhost:8080` | `APP_BASE_URL=https://s.example.com` |
| Database file | `./data/urlshortener` | `spring.datasource.url` in `src/main/resources/application.yml` |

> The Flyway migration is written for H2 (`GENERATED BY DEFAULT AS IDENTITY`, `TIMESTAMP(6)`).
> Moving to MySQL/PostgreSQL means adjusting `src/main/resources/db/migration/V1__create_schema.sql`
> and the datasource properties — nothing else in the code is H2-specific.

### Docker (alternative one-command start)

```bash
docker compose up --build       # http://localhost:8080
```

The H2 file lives in the named volume `shortener-data`, so links survive `docker compose down`.

## 2. API usage

### Create a short link

```bash
curl -i -X POST http://localhost:8080/api/links \
     -H "Content-Type: application/json" \
     -d '{"url": "https://example.com/some/very/long/path?query=1"}'
```

```http
HTTP/1.1 201 Created
```

```json
{
  "code": "aB3xK9",
  "short_url": "http://localhost:8080/aB3xK9",
  "url": "https://example.com/some/very/long/path?query=1",
  "created_at": "2026-10-15T08:30:00.123456Z",
  "expires_at": null
}
```

Validation rules — violations return `400 INVALID_URL`: `url` must be present and non-empty, its
scheme must be `http` or `https`, and its length must be at most 2048 characters.

### Follow a short link

```bash
curl -i http://localhost:8080/aB3xK9
```

```http
HTTP/1.1 302 Found
Location: https://example.com/some/very/long/path?query=1
Cache-Control: no-store
```

### Link details

```bash
curl -i http://localhost:8080/api/links/aB3xK9
```

```json
{
  "code": "aB3xK9",
  "url": "https://example.com/some/very/long/path?query=1",
  "created_at": "2026-10-15T08:30:00.123456Z",
  "expires_at": null,
  "visit_count": 128,
  "last_visited_at": "2026-10-15T09:12:44.001Z"
}
```

### Daily statistics (last 7 days)

```bash
curl -i http://localhost:8080/api/links/aB3xK9/stats
```

```json
{
  "code": "aB3xK9",
  "days": [
    {"date": "2026-10-09", "count": 0},
    {"date": "2026-10-10", "count": 3},
    {"date": "2026-10-11", "count": 0},
    {"date": "2026-10-12", "count": 17},
    {"date": "2026-10-13", "count": 42},
    {"date": "2026-10-14", "count": 51},
    {"date": "2026-10-15", "count": 15}
  ]
}
```

The window covers the **last 7 calendar days including today**, is **ordered oldest → newest**, and
**fills days without visits with `count: 0`**. A "day" is a **UTC** day.

### Errors

Every endpoint returns the same error shape:

```json
{
  "status": 404,
  "error": "NOT_FOUND",
  "message": "No short link with code 'zzzzzzz'",
  "timestamp": "2026-10-15T09:12:44.001Z",
  "path": "/zzzzzzz"
}
```

| Status | `error` | When |
|---|---|---|
| 400 | `INVALID_URL` | URL missing, not http/https, > 2048 chars |
| 400 | `INVALID_CODE` | custom alias is not `[A-Za-z0-9]{3,32}` or is reserved |
| 400 | `INVALID_EXPIRY` | `expires_at` is not in the future |
| 400 | `MALFORMED_JSON` | body is not valid JSON |
| 404 | `NOT_FOUND` | unknown short code |
| 409 | `CODE_ALREADY_EXISTS` | custom alias already taken |
| 410 | `LINK_EXPIRED` | link expired |
| 503 | `CODE_ALLOCATION_FAILED` | could not allocate a free code (retry) |

### Bonus endpoints / fields

| Feature | Usage |
|---|---|
| Custom alias | `{"url": "...", "code": "myalias"}`; taken alias → `409` |
| Expiry | `{"url": "...", "expires_at": "2026-12-31T00:00:00Z"}`; afterwards `GET /{code}` → `410 Gone` |
| List links | `GET /api/links?page=0&size=20` (newest first) — used by the UI |

## 3. Design decisions

### 3.1 Short code generation — random Base62, 7 characters, retry on collision

`SecureRandom` picks 7 characters from `[0-9A-Za-z]` (62⁷ ≈ 3.5 × 10¹² candidates).

- **Why not auto-increment id → Base62?** Sequential codes leak the total number of links and let
  anyone enumerate the entire code space.
- **Why not `hash(url)` truncated?** A hash of the URL is deterministic, which contradicts the
  duplicate-URL policy below (the same URL must be able to receive several codes) and would need an
  extra salt.
- **Collisions:** not prevented but *detected* — the unique constraint on `links.code` rejects a
  duplicate, and the insert is retried with a new candidate (at most 10 attempts, then `503`). Each
  attempt runs in its **own transaction** (`REQUIRES_NEW`); otherwise the failed INSERT would mark
  the ambient transaction rollback-only and make every retry fail.

### 3.2 Redirect status — `302 Found` (not `301`)

`301 Moved Permanently` is cached indefinitely by browsers, so repeat visits never reach the server
and the visit counter silently undercounts — fatal for a service whose job is counting.
`302` forces a round trip on every visit, keeping statistics exact; the price is one extra RTT per
redirect, plus `Cache-Control: no-store` to keep shared caches from replaying the response.
If analytics were not required, `301` would be the better choice (faster, offloads traffic).

### 3.3 Duplicate URLs — always a **new** code

Every submission of the same URL yields a distinct code, so different campaigns/channels get
independent counters and attribution. It also keeps the write path free of a
"lookup-then-insert" upsert race: creation is a single INSERT.
The cost is that identical URLs are stored more than once and there is no global per-URL statistic.
Consequently the `url` column carries **no index** — it is never queried.

### 3.4 Daily statistics storage — per-day aggregate table, not an event log

`link_daily_visit(link_id, visit_day, visit_count)` keeps one row per link per day.

- **Aggregate:** storage is bounded (links × days) and reading the 7-day window is a small range
  scan; for a read-heavy service where redirects outnumber creations by orders of magnitude this is
  the shape that scales.
- **Event log:** would keep every single visit, growing without bound and turning today's hot path
  into tomorrow's full-table scan. Its only advantage is detail we do not need (per-hour slicing,
  unique-visitor counting, recomputing with a different timezone).
- **Atomicity:** the increment is `UPDATE ... SET visit_count = visit_count + 1 WHERE ...`, i.e. the
  arithmetic happens in the database on a single row lock, never as read-modify-write in Java. Both
  counters are written in **one short transaction**; the `UPDATE links WHERE id = ?` for the total is
  executed *first* so that its row lock serialises all concurrent redirects to the same link, which
  makes the "create today's bucket if it is missing" step below practically race-free. When the
  UPDATE matches 0 rows the bucket is created with `count = 1`; should a conflict ever occur (a
  database without row-level locking), the transaction rolls back completely and is replayed once.
  Verified by `RedirectConcurrencyTest` (32 threads × 20 requests, counter exactly 640).
- H2 2.2 supports neither `INSERT ... ON CONFLICT DO UPDATE` nor an atomic `MERGE` with a
  read-then-write subselect, so "update, else insert, retry on conflict" is the portable choice.
- The lifetime `visit_count` on `links` is a deliberately denormalised total: the aggregate table
  alone could not answer "how many visits in total" once old days are pruned.
- **Day boundary: UTC**, so the same visit always lands in the same bucket regardless of where the
  service runs.

### 3.5 Database indexes

| Index | Kind | Why |
|---|---|---|
| `links.code` | UNIQUE | hard guarantee that codes are unique **and** the lookup path for redirect/details/stats |
| `link_daily_visit(link_id, visit_day)` | UNIQUE | makes the daily increment hit one row lock, keeps the 7-day range scan tiny, and prevents duplicate buckets |
| `links.created_at` (DESC) | INDEX | the paginated "latest links" listing used by the UI |
| `links.url` | *(none)* | never queried under the duplicate-URL policy above |

### 3.6 Caching of hot links (bonus)

Caffeine cache `codeToTarget` (`maximumSize=10000`, `expireAfterWrite=10m`) memoises the
`code -> (id, url, expiresAt)` mapping, which is the only thing the redirect hot path needs.
Only **immutable** data is cached and **visit counters are never cached**, so caching cannot distort
statistics. There is no update/delete API, so TTL expiry is sufficient invalidation; the one explicit
`@CacheEvict` fires when a link is found expired. If an edit/delete endpoint were added, it would
have to evict the entry after the transaction commits.

## 6. Note on scaling out (out of scope)

The single instance assumption is what makes H2 acceptable. To scale horizontally you would: move to
PostgreSQL/MySQL and let several stateless app instances share it; keep code allocation as random
inserts (the unique constraint, not a counter, is the source of truth); replace the per-request
increment with a buffered/queued write (e.g. Redis `INCR` flushed periodically, or a batch upsert)
so that a hot link does not serialise on one row; and put the Caffeine cache in front of a shared
read-through layer with explicit invalidation on edit/delete.
